Discussione dei risultati

La strategia 1 (query derivata, fetch LAZY di default) soffre del problema N+1: per ogni partita restituita dalla query iniziale, Hibernate esegue una query separata per caricare squadraHome e una per squadraAway, per un totale di circa 1 + 2N query (dove N è il numero di partite del torneo).

Le strategie 2 (JOIN FETCH in una query JPQL scritta a mano) e 3 (@EntityGraph applicato al metodo del repository) risolvono il problema caricando partite e squadre associate in un'unica query SQL con dei JOIN, indipendentemente dal numero di partite. Il numero di query eseguite nella tabella sopra dovrebbe quindi restare costante (tipicamente 1) per entrambe, mentre cresce linearmente con N per la strategia 1.

Il tempo in millisecondi è indicativo: su un dataset di test piccolo può essere rumoroso (poche query in più o in meno pesano relativamente poco sul tempo totale), ma il numero di query è una prova oggettiva e riproducibile della differenza tra le strategie, indipendente dal carico della macchina in quel momento.
